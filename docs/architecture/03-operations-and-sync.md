# 03 — Operations and sync

## 1. The vocabulary

Twelve operations describe everything a user can do to the tree. They live in
`@cascade/schema` and are the only currency crossing any boundary: client to
server, server to client, undo stack, extension API, audit log.

```ts
// packages/schema/src/operation.ts
export type Operation =
	// structure
	| { kind: "node.create";  nodeId: NodeId; parentId: NodeId; sortKey: SortKey; node: NodeInit }
	| { kind: "node.move";    nodeId: NodeId; parentId: NodeId; sortKey: SortKey }
	| { kind: "node.reorder"; parentId: NodeId; keys: ReadonlyArray<readonly [NodeId, SortKey]> }
	// content
	| { kind: "node.setContent"; nodeId: NodeId; content: readonly Inline[] }
	| { kind: "node.setNote";    nodeId: NodeId; note: readonly Inline[] }
	| { kind: "node.setKind";    nodeId: NodeId; nodeKind: NodeKind }
	| { kind: "node.setAttribute"; nodeId: NodeId; namespace: string; value: Json | null }
	// lifecycle
	| { kind: "node.delete";  nodeId: NodeId; trashSortKey: SortKey }
	| { kind: "node.restore"; nodeId: NodeId; parentId: NodeId; sortKey: SortKey }
	// composite text editing, kept separate because the caret semantics differ
	| { kind: "node.split"; nodeId: NodeId; newNodeId: NodeId; offset: number; sortKey: SortKey }
	| { kind: "node.merge"; nodeId: NodeId; intoNodeId: NodeId }
	// mirrors
	| { kind: "node.mirror"; nodeId: NodeId; sourceId: NodeId; parentId: NodeId; sortKey: SortKey };
```

Design rules, each of which pays for itself later:

- **Ids are generated by the client**, before the operation is sent. The client
  can render the new node immediately, and a retried create is idempotent
  because it carries the same id.
- **Operations are absolute, not relative.** `move` names the destination parent
  and key rather than "indent one level". A relative operation means something
  different depending on when it is applied, which makes replay and rebase
  unsound.
- **Operations do not carry their own inverse.** The inverse is computed
  against the state *before* applying, by `invert(op, stateBefore)`. Putting
  undo data on the wire doubles payload size for a feature only the originating
  client needs.
- **A user gesture may produce several operations**, grouped into a
  transaction (§3). Pressing Tab on a top-level node with a collapsed previous
  sibling is a `move` plus a view-state change; splitting a node mid-text is a
  `split` whose children stay with the original.

`node.delete` is a move into the workspace trash, so it carries the sort key it
lands on and nothing else; the `deleted_at` / `deleted_root_id` stamping of the
subtree is the server's derived work, not part of the wire format
([02 §7](./02-data-model.md#7-deletion-is-a-move)).

`node.reorder` exists so that rebalancing sort keys (see
[02 §3](./02-data-model.md#3-sibling-ordering)) is expressible without emitting
one move per sibling.

Note what is *not* in the vocabulary: nothing about collapse, focus, scroll or
selection. Those are per-user view state
([02 §2](./02-data-model.md#per-user-view-state)), they do not belong in a
shared log, and putting them there is what makes collaborative undo behave
bizarrely.

## 2. Applying operations

One function, used in three places:

```ts
// packages/core/src/apply.ts
export function apply(
	state: TreeState,
	op: Operation,
	ctx: OpContext,
): Result<ApplyOutcome, ApplyError>;

export interface ApplyOutcome {
	readonly state: TreeState;
	readonly inverse: Operation;
	readonly selection: SelectionEffect;   // where the caret should end up
	readonly touched: ReadonlySet<NodeId>; // for fine-grained re-render
}
```

- **Client**, optimistically, the moment the user acts.
- **Server**, authoritatively, inside the workspace lock.
- **Client again**, when replaying pending operations after a rejection or a
  reconnect.

`apply` never throws for a domain problem — it returns
`Err({ type: "cycle" | "missingNode" | "notPermitted" | … })`. Throwing is
reserved for bugs. This distinction matters at the sync layer, which must decide
between "retry", "drop this operation and tell the user", and "crash loudly".

`SelectionEffect` is the piece most implementations forget. Indent must keep the
caret at the same character offset; merge must place it at the join point;
delete must move it to the previous visible row. Encoding that in the return
value keeps caret logic pure and testable instead of scattered across DOM event
handlers.

## 3. Transactions

```ts
export interface Transaction {
	readonly id: TransactionId;
	readonly clientId: ClientId;
	readonly clientSeq: number;      // monotonic per client; the idempotency key
	readonly ops: readonly Operation[];
	readonly origin: "user" | "sync" | "extension" | "migration";
	readonly undoable: boolean;
}
```

A transaction is the unit of atomicity, of undo, and of the network. The server
applies all operations or none. The undo stack pushes one entry per transaction,
so undoing a paste of 40 nodes is one keypress.

`origin` drives policy: `sync` transactions never enter the local undo stack;
`extension` transactions are attributed to the extension in history;
`migration` transactions skip validation that would reject legacy data.

## 4. Sync model

**Server-authoritative log with optimistic local apply.** The client keeps two
things: the last acknowledged server state, and a queue of pending
transactions.

```
local state = fold(apply, confirmedState, pendingTransactions)
```

The loop:

1. User acts → transaction applied locally → rendered → appended to the pending
   queue and persisted to IndexedDB.
2. The queue is drained to the server in order. The server takes the workspace
   lock, re-applies each operation authoritatively, writes the node rows and the
   log entry, and returns the assigned `seq`.
3. The client subscribes to `seq > cursor` (SSE or WebSocket, with polling as
   the fallback). Incoming transactions from other clients — and the
   confirmation of its own — advance `confirmedState`.
4. After each advance, pending transactions are **rebased**: re-applied on top
   of the new confirmed state. Any that now fail (`missingNode` because someone
   deleted the target; `cycle` because someone moved a subtree) are dropped, and
   the user is told what happened.

Why this rather than a CRDT today: the server stays the arbiter, so permissions,
validation and business rules have one place to live; the data stays queryable
SQL rather than an opaque binary blob; and debugging is reading a table. The
cost is that offline edits can be rejected — acceptable, because rejection is
rare and the vocabulary makes each rejection explainable ("this node was deleted
by Alice"). The same shape is what
[TanStack DB](https://tanstack.com/db/latest/docs/guides/mutations) implements
generically; adopting it later is a swap of the queue implementation, not of the
model.

**Idempotency** is `(client_id, client_seq)`, enforced by a unique index. A retry
after a timeout returns the original result instead of duplicating the change.
This is why ids are client-generated: without it, a retried create makes two
nodes and nobody notices until the outline has doubled.

**Ordering** is per client. Transaction 7 must not be applied before 6, or a
move can reference a node that does not exist yet. The queue is strictly
sequential; a permanently failing transaction blocks its successors and must be
surfaced, not skipped.

## 5. Conflicts, concretely

| Concurrent pair | Resolution | Rationale |
|---|---|---|
| Two edits to the same node's content | Last write wins on the whole `content` array, by server `seq` | Node text is a sentence, not a document; character-level merge is disproportionate. §7 upgrades this if it hurts |
| Two edits to *different* attributes | Both survive — `setAttribute` is per namespace | A todo plugin and a due-date plugin must not clobber each other |
| Move A under B, and B under A | Second one loses: rejected as `cycle` | The workspace lock makes the second move see the first |
| Move a node, delete its parent | Node ends up in the trash with the parent; the move applies first if it sequenced first | Consistent because both are moves |
| Delete a node, edit it | Edit applies to a trashed node and is preserved | Restoring must not lose the text; discarding edits is the surprising behaviour |
| Two inserts at the same position | Both survive, order decided by `(sort_key, id)` | Deterministic on every replica, which is the actual requirement |

Every row of that table is a test in `@cascade/core`. They are cheap to write
because `apply` is pure.

## 6. Versioning the vocabulary

The log is permanent, so the operation format is a public API from the first
write.

- **Add, never reinterpret.** A new field must be optional with a defined
  meaning when absent. If the semantics of an existing `kind` change, introduce
  `node.moveV2` and keep the old one applying with its old meaning.
- **Payloads are validated on read**, not trusted. `parseOperation` is the same
  function on both sides, and unknown `kind`s from a newer client are rejected
  with a "please reload" signal rather than being partially applied.
- **`payload` in the `mutation` table stores the operation exactly as sent**,
  including fields this server version does not understand — a newer client
  talking to a lagging replica must not have its data silently trimmed.
- Extension attributes carry their own `v` field inside their namespace, so an
  extension migrates its data independently of the core schema
  ([06 §7](./06-extensibility.md#7-versioning-and-data-migration)).

## 7. If and when we need a CRDT

Two pressures could force a change: true peer-to-peer or long-offline editing
where rejection is unacceptable, and character-level co-editing inside a single
node.

The design keeps both cheap:

**Per-node text.** Because content is per node and independently addressed, a
text CRDT can be introduced for `content` alone, leaving tree operations
untouched. `node.setContent` gains a sibling `node.applyTextDelta` and the node
gains a CRDT state column. Nothing else changes.

**Tree structure.** The literature solution is Kleppmann's *highly-available move
operation*: operations carry Lamport timestamps and are kept in a totally
ordered log; when an operation arrives out of order, the replica **undoes** the
later operations, applies the new one, and **redoes** them. Each move first
checks whether the destination is a descendant of the moved node and, if so,
does nothing. That single rule guarantees no cycles and that every replica
converges. Loro's implementation adds sortable children by combining the movable
tree with fractional indices — the same `sort_key` we already store.

Our vocabulary is deliberately shaped to fit: absolute moves, client-generated
ids, deletion expressed as a move, and sibling order as a fractional index. The
work to adopt it is replacing the pending-queue rebase with an undo/redo log and
adding a Lamport clock — not redesigning the data.

What we would give up: SQL-queryable structure (the tree becomes a materialized
projection of the CRDT), a much larger dependency, and harder debugging. That is
why it is a later decision, made against evidence rather than in advance.

Reference: [Kleppmann et al., *A highly-available move operation for replicated
trees*](https://martin.kleppmann.com/papers/move-op.pdf);
[Loro's movable tree](https://loro.dev/blog/movable-tree).

## 8. Undo

Undo is per user and **selective**: it must undo *my* last transaction, even
when other people have edited since. The global "last transaction" belongs to
whoever typed most recently, and undoing it would be indefensible.

```ts
class UndoStack {
	// Entries hold the inverse ops computed at apply time, plus the selection
	// to restore. They are rebased as remote transactions arrive.
	undo(): Transaction | null;
	redo(): Transaction | null;
}
```

Rules that keep it sane:

- An inverse is recomputed against current state when it is popped, not blindly
  replayed. Undoing a move whose target parent has since been trashed re-parents
  to the nearest live ancestor rather than failing.
- If an inverse is no longer meaningful (the node was hard-deleted), the entry
  is discarded and undo moves to the next one. Silently doing nothing is worse
  than skipping.
- Remote transactions never enter the stack, but they may invalidate entries in
  it — the stack is filtered on every confirmed advance.
- Text typing is coalesced into one undo entry per burst (idle timeout or
  boundary character), matching what every editor does. The coalescing happens
  when *pushing*, so the wire format is unaffected.

## 9. Transport

- **Writes**: oRPC procedure `mutation.push({ transactions })`, returning per
  transaction `{ ok, seq } | { ok: false, error }`. Contract-first, so the
  client's types come from the same object the server implements
  ([05](./05-type-safety.md#5-the-api-contract)).
- **Reads**: `sync.pull({ workspaceId, cursor })` for catch-up, plus a
  server-sent-events stream for live updates. SSE over WebSocket because the
  traffic is one-directional (writes go over normal RPC), it survives proxies,
  and it reconnects with `Last-Event-ID` for free. Revisit if presence and
  cursors arrive, which are genuinely bidirectional.
- **Initial load**: a snapshot endpoint returning the zoom root's visible window
  ([02 §9](./02-data-model.md#9-queries-the-application-actually-runs)) plus the
  current `seq`, so the stream can be joined without a gap.
- **Offline**: pending transactions and the last snapshot live in IndexedDB. On
  boot the client renders the snapshot with pending applied on top, before the
  network is consulted.
